# «Древо»: единая цель и готовность к публикации

Обновлено 2026-11-27. Сверено с исходным ТЗ из файла пользователя, общей ссылкой на чат, текущей веткой `motion-polish-20261124`, PR #262 и объединённым в эту ветку PR #263.

## Цель

Завершить модернизацию всей генеалогической платформы: сохранить интерактивный 3D-атлас главным экраном, объединить его с семейными и личными древами, довести единый дизайн и редактор, сделать статистику честной, защитить семейные данные, сохранить старые ссылки и подготовить публикацию с проверяемым порядком действий и откатом. Саморегистрация — одна из функций, а не цель проекта.

PR #263 был слит в `motion-polish-20261124` коммитом `144d3d04`; этот коммит входит в текущую ветку PR #262. В него вошли усиленная авторизация управляющего, серверные метрики кабинета, очистка PWA-кэша от частных снимков и выдача семейных фотографий через серверную проверку сессии.

## Уже реализовано

- `/atlas/` — точка входа с четырьмя действиями: создать древо, войти, посмотреть демо, исследовать атлас. Трёхмерная карта остаётся центральной функцией. `/nek/`, `/t/` и приглашения ведут в совместимый поток.
- Личный пользователь регистрируется, подтверждает почту и может один раз создать древо без обязательного знания тухума, тейпа или селения. `/trees/` остаётся кабинетом владельца/администратора, а не мастером создания личного древа.
- Вход, выход и смена аккаунта доступны в соответствующих семейном и личном сценариях. «Запомнить меня» сохраняет выбранный вход и email; семейный пароль и личная сессия разделены.
- Управляющие функции ограничены явным серверным allowlist. Семейные API требуют проверенной сессии; редактирование без сессии или при ошибке API не переключается на публичный локальный снимок. Фото выдаются через серверный endpoint с проверкой доступа.
- Для личного древа добавлены приватные отметки мест и заметки; семейные места не появляются автоматически в открытой карте. Разрешённые метки на карте используют только проверенные place ID и тип.
- Личная статистика считается по записям собственного серверного древа; если ранний предок неизвестен, фиктивная дата не подставляется. Ошибка подсчёта мест отдельного тейпа исправлена.
- Общие Motion/UI-стили, SVG-контролы, настройки темы и шаблон редактора распространены на существующие и будущие деревья. В шаблоне таджвид-редактора заменены декоративные стрелки и крестики на доступные SVG; отдельный SVG-размер/обводка применяются и в обычном режиме редактора. Service Worker обновляет согласованные версии и не кэширует семейные снимки и фотографии как публичные ресурсы.
- Вход защищён серверным лимитом семейных попыток и отзывом семейных сессий. Личный пароль ограничен минимумом 15 и максимумом 128 символов на клиенте и серверном пути регистрации. Создание второго личного древа ограничено сервером.
- Семейный редактор получил отдельное окно самоаттестации grant/revoke; журнал согласий хранится в закрытой схеме и доступен только серверному RPC. Администратор `super` не считается представителем семьи. Публичная сводка строится сервером только при явном флаге, совпадающем `DREWO_PRIVATE_REPO` и подтверждении GitHub, что источник приватный; в публичный ответ попадают только крупные интервалы проекта, без ID семей. Флаг по умолчанию выключен. Ручной deploy workflow больше не подменяет общий `GITHUB_REPO` и `GITHUB_TOKEN`, которые могут использовать другие Edge Functions.

## Миграции

В production-журнале чтением проверены три уже применённые Drewo-миграции: `20261124113244`, `20261124113604`, `20261124113705`. В тестовом окружении выполнять следующие файлы строго в этом порядке:

1. `supabase/migrations/20261126_drewo_password_budget.sql` — приватный общий лимит попыток входа в семейные пароли.
2. `supabase/migrations/20261127_drewo_session_revocations.sql` — хранение отозванных семейных сессий до срока истечения.
3. `supabase/migrations/20261127120000_drewo_plus_one_tree_once.sql` — запрет второго личного древа и удаления строки древа через API.
4. `supabase/migrations/20261127183522_drewo_plus_person_places.sql` — приватные места людей личного древа.
5. `supabase/migrations/20261127202119_drewo_aggregate_consent.sql` — журнал grant/revoke без имён, ролевая проверка и server-only RPC.
6. `supabase/migrations/20261128_drewo_family_places.sql` — семейные места, читаемые/изменяемые только серверной функцией.

В локальном тесте эти шесть файлов применялись после трёх production-миграций на одноразовой PostgreSQL 16. Это подтверждает синтаксис и тестовый контракт, но не «полный Supabase-контур» и не соответствие текущей production-базы. `down`-миграций нет. Нельзя удалять строки отозванных сессий, пока токены могут действовать: это восстановит доступ. Журнал согласий нужно сохранять для аудита; отзывать доступ следует новой записью, не удалением события.

## План выпуска после единого одобрения

До одобрения не меняются production-данные и Auth, не переносятся живые семейные данные, не сливается PR #262 и не выполняется production deploy. После подготовки точного target SHA и повторного прохождения локальных тестов запросить одно одобрение на пакет. Действовать после него в следующем порядке и останавливаться при первом провале критерия:

1. Зафиксировать целевой SHA PR #262 и сохранить полный перечень ссылок/переменных окружения без значений секретов. Подготовить проверенный DB backup и процедуру восстановления.
2. Создать приватное семейное Git-хранилище и отдельный минимально привилегированный токен; сначала выполнить только метаданные:
   `node scripts/prepare-drewo-private-repo.mjs --source "$PWD" --ref <target-sha>`.
   Для копирования в заранее созданный защищённый каталог:
   `node scripts/prepare-drewo-private-repo.mjs --source "$PWD" --ref <target-sha> --destination <secure-parent>/drewo-family-<target-sha>`.
   Скрипт не удаляет источник; создаёт каталог `0700`, файлы `0600`, проверяет Git object hash и падает на неполном registry/snapshot. Не печатать список содержимого или данные семьи в CI-лог.
3. На отдельном Supabase применить три исходные и шесть перечисленных миграций через проектный migration runner; прогнать полный Auth/RLS/Edge сценарий на синтетических аккаунтах, включая grant/revoke и публичную сводку. Выпуск остановить, если хотя бы одна роль/семья видит чужие строки или production migration journal отличается от сверенного.
4. Подтвердить и выставить в production Auth-конфигурации: Site URL `https://waydean.ru/atlas/`; exact Redirect URL для подтверждения email `https://waydean.ru/atlas/` (client возвращает на этот путь с `owner=continue` и `remember=0|1`); минимальный пароль 15, максимум 128; CAPTCHA для регистрационных/чувствительных auth-действий, если provider настроен; Supabase Auth rate limits не повышать; email confirmation и SMTP проверить тестовым письмом. Включить leaked-password protection, если она доступна плану. Значения secret/provider keys не записывать в PR.
5. Настроить Edge Function через `.github/workflows/deploy-supabase-publish-drewo.yml`: задать секреты `DREWO_PRIVATE_REPO` и `DREWO_PRIVATE_REPO_TOKEN` для одного подтверждённо private repo, а также `DREWO_AGGREGATE_STATS_ENABLED` (при отсутствии workflow безопасно установит `false`). Workflow проверяет GitHub `private: true`, записывает отдельные `DREWO_GITHUB_TOKEN`/`DREWO_PRIVATE_REPO` и не меняет общие `GITHUB_REPO`/`GITHUB_TOKEN`, используемые `publish-content`. Токен ограничить нужными чтением/записью. Проверить `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `DREWO_SESSION_SECRET`, `DREWO_VAULT_KEY`, `DREWO_HUB_USER_IDS` и legacy password secrets. Оставить `DREWO_AGGREGATE_STATS_ENABLED=false` до checksum-проверки переноса; затем включать только после проверки GitHub `private: true` и успешного синтетического grant/revoke. Проверить allowlist, семейные фото и серверное чтение. Секреты передавать только secret manager.
6. Собрать Pages: `node scripts/prepare-pages-artifact.mjs --release`; он пересоздаёт только `dist/pages`, удаляя его прежнее содержимое. Запустить release/privacy и consent тесты, сверить, что private paths/embedded data отсутствуют, а два удалённых маршрута показывают только tombstone.
7. Проверить историю всех публичных refs и секреты до/после миграции. История публичного Git не станет приватной от пересборки Pages; очистка истории, если потребуется, выполняется только после проверенной private copy, с отдельной резервной копией refs и согласованным окном переписывания/force-push.
8. До переключения трафика ограничить запись и заранее сообщить окном обслуживания, сделать финальный backup. Проверить основной сценарий Atlas, личное дерево, семейный вход/выход и старые маршруты с тестовыми данными.
