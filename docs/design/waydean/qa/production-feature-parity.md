# Waydean «Древо» — матрица сохранения функций

**Версия:** 0.1<br>
**Дата:** 2026-09-30<br>
**Статус:** аудит исходного кода и сопоставление с дизайн-пакетом; локальная регрессия нового UI не пройдена; production не проверялся и не менялся.

## Назначение и границы

Этот документ фиксирует функции, найденные в checkout проекта `QuranAppWebsite` в каталоге `drewo/`, и показывает, где они уже отражены в Waydean Design Bible, Masters и prototype. Это **не подтверждение**, что локальный checkout полностью совпадает с развёрнутым production или что все найденные пути сейчас успешно работают на сервере. Перед интеграцией нужно сверить фактическую production-версию и подтвердить спорные строки.

Новый mobile/desktop prototype использует вымышленные записи и не подключён к серверу, Supabase или текущему хранилищу. Поэтому визуально показанная функция не считается перенесённой, пока не определены её реальное поведение, доступ, сохранение и проверка.

Для отсутствующих экранов составлен [черновик production-потоков](../components/production-flows.md). Он описывает предлагаемые входы и состояния, но ещё не является утверждённым Master и не меняет статусы покрытия в таблице. Отдельный read-only preview локально использует полный JSON для проверки плотности древа и не выполняет запись.

Обозначения покрытия:

- **Покрыто для просмотра** — состояние уже показано в Master или prototype; это не означает, что реализовано production-поведение.
- **Частично** — видна часть сценария, но нет полного соответствия действующему flow.
- **Не спроектировано** — нужен экран или состояние до разработки нового рабочего интерфейса.
- **Сверить** — по именам контролов исходника нельзя заключить, работает ли такое же поведение в production.

## Порядок безопасной проверки

1. **Подтвердить baseline.** Сверить текущий production-релиз/исходный commit с checkout `drewo/`; отметить строки, которые реально присутствуют и доступны пользователям. README и исходник сами по себе не доказывают состояние live-сайта.
2. **Закрыть дизайн-пробелы.** Для каждой подтверждённой строки указать конкретное место входа на desktop и mobile, состояния, права, ошибки и поведение сохранения. Не снимать действующий вход, пока новая точка входа не готова.
3. **Прогнать безопасную локальную регрессию.** Использовать только synthetic fixture и mock API для просмотра, поиска, навигации, форм и ошибок. Prototype не подключать к производственной базе или хранилищу.
4. **Проверить мутации в изолированном staging.** Отдельные тестовые аккаунт, backend, storage bucket, ссылки и push endpoint; покрыть запись, merge, фото, историю, backup/restore и доступ. Если staging не настроен, эти строки остаются блокирующими и непроверенными.
5. **Отдельно провести визуальную и нагрузочную проверку.** Screenshot/pixel review делать относительно утверждённых Desktop/Mobile Master. Проверку ~157 записей и целевых устройств учитывать как отдельный performance gate из [qa/performance-gate.md](performance-gate.md), а не заменять ею функциональную регрессию.
6. **Перед production cutover.** В матрице у каждой подтверждённой функции должны быть место в UI, пройденный локальный тест, staging-результат для серверной операции и план возврата. Production публикуется только после явного утверждения проверенного результата пользователем, согласно [главной спецификации](../product-design-spec.md#L181).

## Что уже выяснено

- Основные сценарии просмотра дерева, профиля, поиска и выбора себя представлены в дизайн-пакете.
- Крупный разрыв перед реализацией — нет экранов входа, редактирования, сохранения, истории, резервных копий, администрирования и PWA-настроек.
- Наличие фильтров, статистики, мини-карты, погоды, ограничений попыток и экспорта нужно подтвердить против реально развёрнутой версии, а не выводить только из имён функций или макетов.

Не запускай весь набор тестов, пока проверка реальных данных не отделена от synthetic fixture: `drewo/waydean-preview-model.test.mjs` содержит кейс, читающий `drewo/family-tree.json`. Не выводи содержимое этого JSON в консоль, логи или артефакты.
