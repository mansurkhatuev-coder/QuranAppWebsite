# Production adapter contract — Waydean «Древо»

**Версия:** draft v0.2  
**Сверка кода:** 2026-10-05, checkout `codex/waydean-mobile-master-preview` на `e6718a2`  
**Статус:** контракт для additive Premium-интеграции (решение обновлено 2026-10-10). В локальном кандидате есть admin-only read-only preview: кнопка показывается для роли `super`, а маршрут подтверждает подписанную сессию существующим действием `auth`. Код-кандидат ещё не опубликован. Live production проверен только по публичной шапке и заголовкам tree JSON response; поведение ролей и API не проверялось. См. [read-only baseline](../qa/live-production-baseline-2026-10-10.md).

## 1. Задача и границы

Новый Waydean UI добавляется как премиум-режим рядом с текущим продуктом; текущий `drewo/` сохраняется как основной бесплатный/совместимый путь и fallback. Для временного теста владельца действует отдельный read-only маршрут, закрытый ролью `super`; полноценная интеграция с правом редактирования и подпиской требует отдельной приёмки. Источником истины остаётся существующий сервис и его текущий формат. Не переносить семейные данные в новую базу, не менять схему дерева и не писать в production напрямую из макетов.

Все будущие операции проходят через один адаптер данных. UI передаёт ему типизированные намерения — загрузить дерево, проверить сессию, сохранить черновик, добавить фото, получить список снимков. Только адаптер знает адрес Edge Function, тело запросов, преобразование дерева и обработку серверных ошибок. Компоненты не вызывают Supabase/GitHub сами и не получают service key, GitHub token или другие серверные секреты.

Для пользовательского теста выбрана отдельная кнопка `Waydean · тест` в текущем древе, а не переключатель темы «Премиум». Открытие доступно только после серверного ответа с ролью `super`; новый preview повторно проверяет подписанный токен и совпадение `treeDir` до чтения данных. Это ограниченный read-only тест, не подписка и не готовое право Premium. Подключение записи в production и публичный платный доступ требуют отдельной проверки и решения.

**Уточнение по текущему checkout (2026-10-10):** существующий вход `login-tree` — это логин семейного дерева и пароль. Подписанная сессия содержит `treeDir`, `role`, срок и отпечаток пароля; стабильного идентификатора личного аккаунта в этом контракте нет. Для временного теста выбран существующий серверный `role: super` с проверкой точного `treeDir`; это не переносит пароль или токен в URL и не означает Premium entitlement. Если позднее понадобится персональный аккаунт/подписка, потребуется отдельный entitlement-контракт.

**Admin-preview slice (2026-10-10):** текущая страница сохраняет выданный сервером session token в `sessionStorage`. Кнопка появляется только после ответа с `role: super`; маршрут `?source=account` отправляет token на существующее действие `auth`, проверяет `ok`, `role === "super"` и совпадение `treeDir`, и лишь затем загружает дерево. Endpoint указывается в `meta[name="waydean-publish-api"]`; preview не использует API записи. Клиентское скрытие кнопки служит удобству, а серверная проверка закрывает прямой переход по URL.

### Доступ к Waydean и будущая оплата

- Доступ к admin-preview проверяет сервер на основе подписанной сессии и роли `super`; query-параметр и клиентская видимость не являются разрешением.
- Роль `super` используется только для временного теста чтения. Перед включением сохранения изменений или подписок нужен отдельный staging, проверенная привязка владельца и серверное entitlement-решение.
- При отсутствии права текущий продукт продолжает открываться без потери данных. Ошибка проверки права должна безопасно вести к старому экрану или понятному сообщению.
- Будущий платёжный сервис обновляет entitlement только серверным подтверждением/webhook. Клиент Waydean зависит от общего ответа `allowed / denied / unavailable`, а не от SDK или названия provider.
- Административная read-only проверка разрешена только для маршрута preview. Она не подключает production-запись и не означает, что платный entitlement уже существует.

## 2. Текущий путь данных в checkout

```text
drewo/index.html
  ├─ чтение: ./family-tree.json и встроенный #tree-data
  ├─ состояние доступа: ./access.json + sessionStorage токен Некъ
  └─ запись/операции: POST Supabase Edge Function publish-drewo
       └─ сервер проверяет роль → создаёт GitHub commit → обновляет статические файлы,
          резервные копии и фото; публикация Pages происходит отдельным workflow
```

Ссылки на исходник: [загрузка дерева](../../../../drewo/index.html#L6514), [сериализация дерева](../../../../drewo/index.html#L5573), [Edge Function URL и контекст](../../../../drewo/index.html#L4607), [функция API-вызова](../../../../drewo/index.html#L6995), [серверная Edge Function](../../../../supabase/functions/publish-drewo/index.ts).

### Формат дерева

- Сохранять существующее дерево как вложенную структуру с корнем и списками потомков `sons`. Плоский список `id/parent` допустим только как временная модель интерфейса.
- При записи сериализовать обратно через совместимое преобразование. Не отправлять UI-поля `allowAdd`, временные поля с `_` или новые поля без отдельной миграционной проверки.
- Даты, имена, заметки, связи, порядок потомков, маркер версии фото и `activity-log` должны сохраняться без потери. `family-tree.json` и встроенный `#tree-data` должны оставаться согласованными.

### Доступ и сессия

| Действие | Что делает текущий клиент | Требование к адаптеру |
| --- | --- | --- |
| `login-tree` | Передаёт логин и пароль; получает `treeDir`, путь и подписанный session token; для другого дерева перенаправляет на его путь | Не сохранять пароль в URL/логе; связывать дальнейшую сессию только с `treeDir`, возвращённым сервером |
| `auth` | Проверяет пароль или session token для `treeDir`; получает роль, состояние блокировки и новый токен | Сервер является единственным источником роли и срока сессии; UI-роль сама по себе не даёт полномочий |
| `status` | Получает открытое состояние блокировки/оплаты и причину | Считать только информацией интерфейса, а не доказательством права на чтение или запись |

Старый клиент хранит токен в `sessionStorage` и убирает `?nek=` из адреса после чтения. Токен истекает и привязан к отпечатку текущего пароля; смена пароля делает старую сессию недействительной. См. [клиентскую обработку сессии](../../../../drewo/index.html#L4886) и [серверную проверку](../../../../supabase/functions/publish-drewo/session.ts).

**Подтверждённая граница текущего checkout:** дерево читается из статического `family-tree.json` без проверки пользователя в браузерной функции `fetchRemoteTree()`. Также код знает публичный fallback bucket фотографий. Клиентский login overlay не закрывает прямое чтение статического URL. До переноса не делать заявления о приватности; на staging проверить фактический доступ к JSON, access-файлу и фотографиям. Открытая CORS policy Edge Function также не заменяет серверную авторизацию.

## 3. Запись дерева и конкурентные изменения

Текущий UI отправляет `action: "publish"` с полями:

- `treeDir`, `treeJson`, `activityJson`;
- `password` или проверенный `sessionToken`;
- `baseFingerprint` и `baseTreeJson` для сравнения с загруженной версией;
- `photos` (`personId`, `full`, `thumb`) и `photoDeletes`;
- `force` и человекочитаемое `message`.

Сервер проверяет роль, нормализует JSON, при необходимости объединяет изменения и одной GitHub commit-операцией записывает изменившиеся HTML/JSON, snapshot/manifest и фото. Ответ содержит опубликованные tree/activity, новый fingerprint, `merged`, `mergeStats`, число созданных резервных копий, `photosWritten` и `photoDeletesWritten`. Сервер может отдельно сообщить о push-уведомлениях. Сверять точные типы ответа с текущей веткой Edge Function перед реализацией.

### Текущая политика merge — важное ограничение

Если fingerprint изменился, сервер вызывает three-way merge. В [реализации merge](../../../../supabase/functions/publish-drewo/merge-tree.ts) при изменении одного поля обеими сторонами входящее локальное значение побеждает без отдельного конфликта; удаления и перепривязка узлов в этом merge не применяются. Если merge выбрасывает ошибку, API возвращает HTTP 409 с `conflict: true` и снимком серверного дерева.

Адаптер обязан передавать исходный fingerprint и base snapshot, никогда не включать `force` автоматически и не заменять черновик серверным ответом до сохранения локального recovery-копирования. До изменения политики merge нужны отдельные синтетические сценарии: одна и та же правка поля, параллельные добавления, удаление, перепривязка и повтор после 409. До их выполнения не обещать пользователю, что система всегда обнаруживает конфликт.

## 4. Фото, резервные копии и остальные операции

### Фото

- Текущий экран делает JPEG full и thumbnail, помещает их в локальную очередь IndexedDB и меняет маркер `photo` в дереве; удаление ставит ID в очередь. Очереди прикрепляются к следующему `publish`, поэтому «изменено локально» и «сохранено на сервере» — разные состояния.
- Edge Function ожидает для одного фото `personId`, `full` и `thumb` как JPEG data URL; полный и thumbnail файлы получают пути `<treeDir>/photos/<id>.jpg` и `<id>-thumb.jpg`. За один publish сервер ограничивает число новых фото 20, валидирует ID, MIME и размер.
- Удаления передаются отдельно как ID в `photoDeletes`; сервер удаляет full и thumbnail в том же commit, где обновляет дерево. Не считать изменение поля `photo` успешной загрузкой само по себе.
- Очередь очищать только после полного подтверждения всех ожидаемых фото и удалений. При частичном ответе, таймауте, закрытии вкладки или недоступности IndexedDB сохранять черновик и показать восстанавливаемое состояние. Текущий клиент проглатывает ошибку записи фото в IndexedDB — это поведение не копировать в новый адаптер.
- Реальные фото не копировать в fixture, screenshots, Pages, console или QA-артефакты. Использовать разрешённый синтетический набор на staging.

### Backups, locks, password, push

Сохранить серверные действия и учитывать границы ролей, найденные в checkout:

| Действия | Текущая проверка в Edge Function |
| --- | --- |
| `list-backups`, `vapid-public`, `subscribe`, `unsubscribe` | Нужен успешно разрешённый `editor` или `super`; специальная проверка суперроли отсутствует. `status` — отдельный информационный ответ до проверки входа. |
| `publish`, `upload-photo`, `delete-photo`, `snapshot` | Нужен `editor` или `super`. Обычный editor блокируется при lock/billing restriction; `super` обходит эту блокировку. |
| `pin-backup`, `restore` | Нужен `super`, но старый fallback разрешает `editor`, если суперпароль ещё не настроен. Не переносить это исключение в новую систему молча. |
| `set-lock`, `set-password` | Нужен `super`; при ненастроенном суперпароле действие не становится доступным editor и возвращает ошибку настройки. |

Это описание исходного checkout, а не подтверждение фактической конфигурации сервера. Перед staging проверить те же роли на изолированном наборе. Клиентский mock или видимая кнопка не означает, что действие доступно.

Не выполнять `restore`, `set-lock`, `set-password`, подписку push и публикацию на production во время приёмки. Они меняют данные/доступ либо подписывают реальное устройство.

## 5. Целевой интерфейс адаптера

Это логический контракт, не готовый production-код:

```ts
interface ProductionTreeAdapter {
  signIn(login: string, password: string): Promise<Session>;
  restoreSession(): Promise<SessionState>;
  loadTree(session: Session): Promise<TreeSnapshot>;
  saveTree(input: {
    tree: EditableTree;
    activity: ActivityEntry[];
    baseFingerprint: string;
    baseTree: PersistedTree;
    photos: PendingPhoto[];
    photoDeletes: string[];
  }): Promise<SaveResult>;
  listBackups(): Promise<BackupSummary[]>;
  createSnapshot(label?: string): Promise<void>;
  restoreBackup(name: string): Promise<TreeSnapshot>;
  uploadPhoto(personId: string, image: File): Promise<PendingChange>;
  removePhoto(personId: string): Promise<PendingChange>;
}
```

Интерфейс не разрешает производственный обход: нет публичной записи, прямого GitHub API из браузера, постоянного service token, `force` по умолчанию или implicit save при переключении экрана. В каждом ответе различать `dirty`, `saving`, `saved`, `conflict`, `locked`, `unauthorized`, `offline` и recoverable error. До успешного подтверждения сохранения не показывать «Сохранено» и не очищать изменения пользователя.

## 6. План интеграции без риска для production

1. Зафиксировать live baseline read-only: версия приложения, публичность JSON/photo URL, существующие входы, роли, оповещения и поведение публикации. Не выводить реальное дерево в лог.
2. Поднять отдельный staging с синтетическим клоном формата, отдельными GitHub paths/repo и тестовыми секретами. Если изоляция GitHub commit и storage не подтверждена, write-сценарии не запускать.
3. Собрать адаптер в локальном prototype за отдельным флагом режима; старый `drewo/` не удалять. Сначала локально завершить UI без production-доступа.
4. На staging проверить чтение, логин, истечение/отзыв токена, права `editor/super`, обычную запись, фото add/remove, таймаут/повтор, три-way merge, 409, резервную копию/восстановление, lock/unlock и push opt-in.
5. Сверить итоговый JSON до/после по структуре и количеству связей без публикации содержимого, проверить параллельное открытие двух сессий, затем выполнить полную регрессию после согласованного тестового прохода.
6. Только после этого собрать release-кандидат, проверить rollback и запросить отдельное разрешение на production.

## 7. Статус и критерий готовности

- **Локальный кодовый контракт:** описан по `drewo/index.html` и `supabase/functions/publish-drewo`; это не live-подтверждение.
- **Адаптер:** не реализован и не подключён к прототипам.
- **Production baseline и staging:** не проверены / не подтверждены.
- **Тесты:** пользователь отложил до следующего этапа; в этом проходе не запускаются.
- **Production:** не изменять до staging, тестового прохода и отдельного утверждения релиз-кандидата.

Критерий закрытия — новый UI использует тот же контракт без потери дерева, журнала, фото и полномочий; recovery/merge доказаны на staging; полный feature parity и rollback приняты. Успешное локальное чтение синтетического fixture этот критерий не закрывает.
