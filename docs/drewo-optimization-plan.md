# План оптимизации древ (VPN, скорость, сопровождение)

Страницы: `/drewo/` (Хьоти некъ), `/drewo-dada-yurt/` (Дади-Юрт), `/drewo-reklama/` (демо), пульт `/trees/`.

Цель: **одна и та же страница работает и без VPN из РФ, и с VPN**, без ручного переключения. Авторизация, фото, сохранение и открытие древа не должны зависеть от того, какой выход у телефона.

---

## 1. Что сейчас происходит

Браузер ходит сразу в **четыре разных мира**:

| Что видит пользователь | Куда реально идёт запрос | Типично без VPN (РФ) | Типично с VPN |
|---|---|---|---|
| Открыть `waydean.ru/drewo/` | GitHub Pages (A-записи GitHub, `CNAME` = `waydean.ru`) | Часто открывается, иногда тормозит/не резолвится | Иногда **не открывается** (DNS VPN, репутация IP GitHub, блокировка датацентровых VPN) |
| Войти (имя + пароль) | `*.supabase.co/functions/v1/publish-drewo` (`action: auth`) | **Часто недоступен** — вход зависает или «нет связи» | Работает |
| Фото на кружках и в карточке | `*.supabase.co/storage/v1/object/public/drewo-photos/...` | **Не грузятся** | Работают |
| Сохранить дерево, бэкапы, онлайн, визиты | тот же Edge Function | Не работает | Работает |
| Шрифты | `fonts.googleapis.com` / `fonts.gstatic.com` | Часто блокируются | Работают, но `document.fonts.ready` может долго ждать |
| Погода | `api.open-meteo.com` + `api.bigdatacloud.net` | Часто нет | Обычно есть |
| Пульт `/trees/` | ещё и `cdn.jsdelivr.net` (supabase-js) + Auth Supabase | Логин и скрипт могут не загрузиться | Работает |

Это не «баг пароля». Это **разорванный origin**: HTML с GitHub, логика и картинки с AWS/Supabase (регион Frankfurt). В РФ эти сети режутся по-разному. VPN чинит одну половину и ломает другую.

Уже есть намёк в UI: при входе пишется «Если зависло — попробуйте VPN». Это обход, а не решение.

---

## 2. Дополнительные причины «иногда не открывается с VPN»

Даже когда GitHub Pages доступен, страница может казаться мёртвой:

1. **`callPublishApi` без таймаута.** Если `supabase.co` режется, `fetch` висит десятки секунд. Кнопка «Проверяем…», экран «Загружаем древо…».
2. **Лимит входа по IP:** 5 неверных паролей → блок **15 минут на весь IP**. У VPN один выход на сотни людей: один ошибается — остальные «не могут войти».
3. **Тяжёлый первый байт.** `drewo/index.html` ≈ 340–380 КБ, внутри CSS + JS + встроенный JSON дерева. Плюс `bg.jpg` / `bg-night.jpg` / ещё 2 дневных фона. Через VPN это долго.
4. **Три копии одного приложения** (`index.html` на 9–11 тыс. строк). Правки идут через `scripts/patch-drewo-*.py` — легко разъехаться, легко оставить зависание только в одном древе.
5. **Публикация** переписывает HTML через GitHub API и ждёт деплой Pages (~минуты). Пока кэш старый, пользователь думает, что «не сохранилось / не открылось».
6. **Cloudflare Pages выключен** (`.github/workflows/deploy-cloudflare-pages.yml` с `if: false`). Сейчас пользователи бьют напрямую в IP GitHub, без anycast-прокси.

---

## 3. Принцип решения

Браузер должен говорить **только с `waydean.ru`**.

```
телефон  →  https://waydean.ru/drewo/          (HTML/CSS/JS/JSON)
         →  https://waydean.ru/api/drewo       (вход, сохранение, онлайн)
         →  https://waydean.ru/photos/...      (фото)
```

`supabase.co`, `fonts.googleapis.com`, `jsdelivr` с телефона **не вызываются**. Их видит только сервер/воркер.

Тогда неважно, включён VPN или нет: путь один.

## 4. Этапы

### Этап A — Сеть: один origin (главное)

Порядок такой, потому что без него остальные оптимизации не уберут «нужен VPN для входа».

**A1. Вернуть Cloudflare перед доменом (оранжевое облако).**  
DNS `waydean.ru` → Cloudflare, origin = GitHub Pages **или** сразу Cloudflare Pages. Пользователь ходит на anycast CF, а не на A-записи GitHub. Это обычно чинит «с VPN сайт не открывается» и смягчает блокировки GitHub в РФ.

**A2. Worker-прокси API** (в репозитории уже есть образец `qf-proxy/`).  
Новый Worker (или маршрут на существующем):

- `POST /api/drewo` → `https://rivjkiksknnesahrvamf.supabase.co/functions/v1/publish-drewo`
- проброс тела, `Content-Type`, корректный `CF-Connecting-IP` / не схлопывать всех клиентов в один IP воркера
- таймаут 12–15 с, ответ 504 с текстом «сервер не ответил», а не вечный спиннер

В трёх `index.html` заменить:

```js
var PUBLISH_URL = 'https://waydean.ru/api/drewo';
```

**A3. Тот же origin для фото.**

- Worker: `GET /photos/<treeDir>/<file>` → Supabase Storage `drewo-photos`
- либо зеркало в **Cloudflare R2** / папку хостинга при загрузке (`upload-photo` кладёт и туда, и в Storage)

В клиенте:

```js
var PHOTO_PUBLIC_BASE = '/photos';
```

Кружки и лайтбокс больше не зависят от доступности `supabase.co`.

**A4. Шрифты и SDK только со своего домена.**  
Скачать Cormorant Garamond + Source Sans 3 в `/assets/fonts/`. У пульта `/trees/` убрать `cdn.jsdelivr.net`, положить `supabase-js` локально **или** (лучше) не звать Auth Supabase с телефона: пульт тоже ходит в `/api/drewo`.

**A5. Если Cloudflare в конкретном регионе тоже режется:** зеркало статики на российском хостинге (Beget/Timeweb), тот же прокси `/api` и `/photos` nginx’ом. Домен один; это запасной origin, не второй сайт.

Проверка этапа A (с телефона, мобильный интернет, **без** VPN и **с** VPN):

- [ ] открывается `/drewo/`
- [ ] вход по имени + паролю
- [ ] видны уже залитые фото
- [ ] загрузка нового фото
- [ ] «Сохранить»
- [ ] пульт `/trees/` логинится

### Этап B — Не зависать при плохой сети

Делать сразу после A или даже чуть раньше: дёшево и уже уменьшает «не открывается».

1. **Таймаут на все `callPublishApi`** (AbortController, 12 с). Сейчас таймаут есть только у погоды.
2. **Не блокировать показ дерева сетью.** Сессия в `localStorage` уже есть (`drewo-view-session`). Если API недоступен, открывать просмотр из встроенного JSON / `family-tree.json`, а вход/фото помечать «сервер недоступен».
3. **Лимит пароля не по IP VPN.** Ключ: дерево + хеш пароля-попытки + грубый отпечаток устройства, либо учёт в таблице Supabase по `sessionId`. Иначе один чужой fail на общем VPN-выходе закрывает всех.
4. **`document.fonts.ready` не должен держать первый кадр.** Рендер сразу системными шрифтами, перерисовка после загрузки своих woff2.
5. **Presence:** heartbeat 20 с + poll 12 с = лишние запросы на `supabase.co`. После прокси урезать (heartbeat 45–60 с, poll 30 с) или SSE/Realtime через тот же `/api`.
6. **`record-visit` не должен коммитить в GitHub** на каждый визит (сейчас best-effort commit в `access.json`). Счётчик только в таблице; GitHub — редкий снимок. Это снимает гонки с сохранениями дерева и лишние деплои Pages.

---

### Этап C — Скорость открытия

1. **Разрезать монолит.** Один общий `drewo.css` + `drewo.js` (~сейчас 9–11 тыс. строк × 3 файла). В `index.html` оставить разметку и `TREE_DIR`. Патчи-питоном больше не нужны для фич.
2. **Данные отдельно.** Источник правды — `family-tree.json` (он уже есть). Убрать дубль `<script id="tree-data">` из HTML, чтобы публикация не переписывала 350 КБ HTML и не упиралась в кэш Pages.
3. **Фоны:** один день + одна ночь, WebP, `preload` только текущего неба, остальные lazy. Сейчас preload и `bg.jpg`, и `bg-night.jpg`.
4. **Фото:** thumb уже есть (`*-thumb.jpg`); грузить full только в лайтбоксе. `loading="lazy"` / IntersectionObserver на кружки вне экрана.
5. **Кэш:** короткий cache для HTML, длинный для `drewo.js?v=hash`, фото с `?v=` как сейчас.

Ожидаемый эффект: первый экран с десятков секунд на слабом VPN до пары секунд.

---

### Этап D — Сопровождение (после стабильной сети)

1. Общий модуль `TreeModel` / рендер / гейт / фото — одна копия на три древа.
2. Пульт `/trees/` читает `hub-overview` только через `/api/drewo`, без отдельного supabase-js с CDN.
3. Бэкапы: не хранить полные HTML-снимки приложения в `backups/*.html` (они раздувают репозиторий). Только JSON дерева + activity, как уже сделано в поздних бэкапах.
4. Явный статус сети в шапке: «онлайн / сервер недоступен», без требования к пользователю «включите VPN».

---

## 5. Что не делать

- Не оставлять совет «для входа включите VPN, для открытия выключите» — это и есть текущая поломка.
- Не переносить фото обратно в git/HTML: репозиторий и Pages раздуются, деплой станет ещё медленнее.
- Не звать `supabase.co` «на всякий случай» параллельно с прокси: снова получим зависимость от VPN.
- Не включать второй капча/OAuth ради входа семьи: достаточно прокси + нормальный rate-limit.

---

## 6. Рекомендуемый порядок работ

1. Таймаут `fetch` + понятная ошибка (этап B, кусок) — сразу меньше «зависло».
2. Cloudflare на домен + Worker `/api/drewo` и `/photos` + смена URL в трёх древах и пульте (этап A).
3. Самохостинг шрифтов, убрать jsdelivr.
4. Визиты без GitHub-коммита, ослабить presence.
5. Вынести CSS/JS, убрать JSON из HTML (этап C).
6. Общий движок (этап D).

Критерий готовности: с МТС/Мегафон **без VPN** и с типичным VPN (Outline / v2ray / коммерческий) одни и те же действия проходят: открыть, войти, увидеть фото, сохранить.
